Configure it without a rebuild.

A hand-written single page app, embedded straight into the firmware — no npm, no bundler, no framework. It’s the only way to change wiring, network, or lock settings once a board is out of reach of USB.

The setup access point.

With no Wi-Fi credentials stored, the reader starts its own network: Aliro-Setup-XXXX, password aliro1234 by default. Join it and http://192.168.4.1/ should open on its own.

What the UI actually talks to.

MethodRouteDoes
GET/api/configRunning configuration, secrets masked
POST/api/configPatch the configuration — missing keys keep their stored value
POST/api/unlockUnlock now, same as a tap or a Matter command
POST/api/otaUpload a new firmware image, applied with automatic rollback
WS/wsLive status: lock state, taps, network, over one WebSocket

An empty password field in a config patch means “keep the stored one” — passwords are never echoed back to the browser.

Overview, hardware, network, MQTT, OTA, system.

Overview

Live lock state, last tap, and network status over the WebSocket.

Hardware

NFC chip, bus, every pin, lock output and polarity — validated against the target chip before it’s accepted.

Network

Wi-Fi scan and join, plus the setup-AP fallback settings.

MQTT

Broker, credentials, TLS, topics, and Home Assistant discovery — off by default.

OTA

Upload a .bin, watch progress, and get automatic rollback if the new image doesn’t come up clean.

System

Optional HTTP Basic auth, device name, and diagnostics.

Read this before it guards a real door.

Authentication is off by default. A username and password can be set from the System page, and every config and OTA endpoint refuses without it once it’s on — but until you turn it on, anyone on the network can reconfigure the reader, and anyone who can reach it can send an unlock over MQTT if a broker is configured. Fine on a bench driving an LED; not fine on a door.

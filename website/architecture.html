Home / 01 · Architecture

One seam per component.

The firmware is split around the parts expected to change independently: NFC hardware, Aliro transactions, access policy, configuration, and network integrations. New work goes behind an existing seam, or gets a new one — not spread across three.

Transaction path

From RF field to decision.

NFC_TRANSPORT

Poll / activate / exchange. Owns the PN532, the bus, and the RF field lifecycle.

ALIRO_READER

Session + authentication. Wraps Espressif’s Aliro SDK; owns protocol state and crypto sessions.

ACCESS_CONTROL

Identity + policy + lock. Credential lookup and the unlock decision live here — separate from protocol code.

APP_CONFIG → NVS

Persisted settings. Browser edits flow web_server → app_config → NVS; everything else reads from there at boot.

NET / MQTT / MATTER

Optional integrations. Wi-Fi with setup-AP fallback, MQTT with Home Assistant discovery, and an optional Matter Door Lock endpoint.

Why the boundaries

The NFC chip can change without rewriting the reader.

nfc_transport

Hardware isolation

PN532 is implemented today; PN7160 and ST25R3916 don’t share its bus, driver, or quirks. The transport interface keeps those details isolated from everything above it.

aliro_reader

Protocol ownership

Espressif’s Aliro SDK owns protocol state and cryptographic session handling. This project wraps it in a polling task rather than duplicating the protocol.

access_control

Policy, not protocol

Credential lookup and the decision to unlock are policy, kept outside protocol code — room for schedules, revocation, and multiple locks later.

app_config + net_manager

Boot-time truth

Runtime configuration in NVS, Wi-Fi with a setup-AP fallback, and pin validation that refuses wiring that doesn’t exist on the target chip.

matter_lock

Optional Matter

Compiled out unless enabled. Exposes a Matter Door Lock endpoint and the Aliro provisioning feature, so a controller can enroll credentials the standard way.

mqtt_manager + web_server

Operations layer

Lock state, tap events, and commands over MQTT with Home Assistant discovery; a REST API and embedded UI for everything that isn’t provisioned over Matter.

One tap

The reader task owns the session.

Polling, activation, session creation, credential lookup, exchange, and result handling happen in one controlled lifecycle. The result reaches access control only after the field is released.

poll()
  → activate()
  → create Aliro session
  → expedited transaction
      ↳ NFC exchange
      ↳ credential key-slot lookup
  → exchange phase
  → delete session
  → deactivate NFC field
  → access_control_on_reader_result()

Design constraints

Some limits are intentional.

ConstraintReason
One reader sessionThe SDK is singleton-shaped, so callbacks safely route through module state rather than an instance handle.
Boot-time configurationChanging a live SPI bus or lock GPIO mid-transaction is worse than requiring a restart.
NVS firstReader identity, group information, and configuration need persistent storage before the protocol starts.
Network is optionalThe reader stays a reader when Wi-Fi or a controller is unavailable — NFC access doesn’t depend on the network being up.
One PN532, one taskThe transport has exactly one physical chip behind it; anything that needs the bus goes through the same poll loop, sequentially.
